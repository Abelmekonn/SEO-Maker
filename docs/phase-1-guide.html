1. What this is

Two things were built, and they fit together:

173knowledge items, each one claim with a traceable source
7policies — conflicts decided, not left open
8primary sources read end to end
259tests passing (224 core + 35 new)

The knowledge base is a curated corpus of SEO and GEO knowledge. Every item carries the claim, the evidence behind it, the scope where it applies, the scope where it does not, and a citation back to a document archived on disk.

The Phase 1 AI foundation is the machinery that retrieves that knowledge, assembles it with real crawl evidence, calls a model, validates what comes back against a strict contract, caches it, and records it. No feature code ever talks to a model directly.

2. The problem it solves

An SEO tool with an LLM bolted on produces confident nonsense. It says “keep your title under 60 characters” because that sentence appears ten thousand times on the internet — not because Google says it. Google does not say it.

The failure mode. The crawler finds a fact (“this title is 78 characters”). The model fills the gap between fact and advice from its training data, which is a blend of correct documentation and a decade of repeated folklore. The user gets folklore in a tool that looks authoritative.

The fix is to give the model the actual documentation, with the limits attached, and to make it structurally hard to say the folklore. That is what the corpus and the policies are for.

Three real corrections this produced

Widely believedWhat the source actually says
Pages need exactly one H1, in strict heading order “From Google Search perspective, it doesn’t matter if you’re using them out of order… there’s no magical, ideal amount of headings.” — SEO Starter Guide
E-E-A-T is a ranking factor you can improve and measure “Thinking E-E-A-T is a ranking factor. No, it’s not.” — SEO Starter Guide
Google prefers longer content; aim for a word count “Are you writing to a particular word count because you’ve heard Google has a preferred word count? (No, we don’t.)” — helpful-content guidance

Four kinds of knowledge, kept apart

TypeCountMeaning
authoritative129Official documentation or a ratified standard. Requires an official/standard source — the build fails otherwise.
myth19A claim the sources do not support. Exists so the model can contradict it. Never emitted as advice.
research18Studies and benchmarks, with method and population preserved.
heuristic7Practitioner convention. Never presented as an engine requirement.

Three evidence axes, deliberately separate. knowledgeType is what kind of knowledge it is. claimType is how strong the claim is. evidenceStrength is how good the evidence is.

A rater-guideline item is authoritative (Google published it) but only evaluation_criterion (it describes what human raters judge, not what the algorithm does). Collapsing those two is exactly how “E-E-A-T is a ranking factor” gets into a tool.

4. Anatomy of a knowledge item

Here is a real item, trimmed to the fields that matter. This is the one that fires when a site’s robots.txt returns a server error.

{
  "id": "seo-tech-robots-5xx-disallow",
  "knowledgeType": "authoritative",
  "claimType": "specification_rule",
  "evidenceStrength": "strong",

  "title": "A 5xx or unreachable robots.txt means crawlers must assume complete disallow",

  "principle": "RFC 9309 Section 2.3.1.4 states that if robots.txt is unreachable due to
                server or network errors, the file is undefined and the crawler MUST assume
                complete disallow...",

  "whyItMatters": "This is one of the few single-file failures that can take a whole site out
                   of crawl. It deserves the highest technical severity SEO Maker can assign.",

  "appliesWhen":      ["The crawl receives a 5xx response when fetching /robots.txt", ...],
  "doesNotApplyWhen": ["The response is 4xx, which the standard treats as no restrictions", ...],

  "limitations": "Exact retry windows and cache retention vary by implementation; the 30-day
                  figure is an example in the standard, not a required threshold.",

  "checks": ["robots", "robots_audit", "crawl_plan"],

  "source": {
    "name":     "RFC 9309 - Robots Exclusion Protocol",
    "location": "Section 2.3.1.4 (\"Unreachable\" Status), page 8",
    "quote":    "If the robots.txt file is unreachable due to server or network errors, this
                 means the robots.txt file is undefined and the crawler MUST assume complete
                 disallow.",
    "localPath": "knowledge/raw/seo/Robots Exclusion Protocol.pdf"
  }
}

Four fields do the heavy lifting:

  • checks — binds the item to real CheckId values in packages/core/src/scoring/page-audit.ts. This is how retrieval works: an exact join, not a similarity guess.
  • doesNotApplyWhen and limitations — mandatory. An item with no stated limit is usually an overclaim, and the build rejects an empty limitations.
  • source.quote + source.location — present only when the document was actually read. Never fabricated.

The check that makes fabricated citations structurally impossible: the build script refuses to emit the corpus if an item is marked unverified yet carries a quote. You cannot accidentally invent a citation and have it ship.

128 of 173 items are verified against a locally archived source. The other 45 came from the earlier seed, cite documents not in raw/, and carry no quote and no section reference — because none was verified.

5. Policies — the decided conflicts

Extraction turned up seven places where sources disagreed, or where the documentation contradicts what the product’s own code says. Each one is decided, not left as an open question for the model to arbitrate at generation time.

PolicyDecision
policy-word-countThe 300-word threshold is an internal trigger. Never surface the number.
policy-headingsh1/h2 findings are readability and accessibility, never a Google requirement.
policy-title-meta-lengthLength is truncation risk only — never pass/fail, never the lead finding.
policy-ai-eligibilityThree conditions required, including Search Console inclusion, which the crawler cannot check and must say so.
policy-geo-effect-sizesNever quote a GEO percentage. Describe direction only.
policy-geo-content-tacticsRecommend sources, quotes and data. Refuse authoritative-tone rewriting.
policy-4xx-removalUse the semantically correct status code. No removal-speed claim for 410.

A policy in full

{
  "id": "policy-word-count",
  "decision": "The 300-word threshold is an internal trigger. Never surface the number.",

  "rationale": "Three separate Google documents deny a preferred word count — 'No, we don't',
                'no magical word count target', 'no ideal page length'. A threshold is still
                needed to make thinness computable, but it detects a candidate problem rather
                than defining a standard the page must meet.",

  "directive": "When the threshold fires, read the page and report what is actually missing...
                If the page is functional — a login, a converter, a category page — suppress
                the finding entirely.",

  "neverSay": [
    "This page is under 300 words.",
    "Expand this page past 300 words.",
    "Google prefers longer content."
  ],

  "losingClaim": "Pages need a minimum word count to perform in search.",
  "appliesToChecks": ["words"]
}

losingClaim is kept deliberately: when a user or a competitor’s report raises the rejected position, the model can recognise and contradict it rather than agreeing.

Four of these override the product’s own wording. The h1 check hint says “Has one H1”; the title recommendation says “roughly 50-60 characters”; the words recommendation says “Expand the page past 300 words”. These are not code bugs — a threshold is what makes a check computable — but the AI layer must not restate them as Google rules. That is what the policies enforce.

6. Phase 1: the AI foundation

Phase 0 was already complete and verified before any of this started: the crawler retains real page text, heading text, links with anchors, parsed JSON-LD and image metadata; business context and Quick/Deep modes exist; all 224 existing tests pass.

Phase 1 built the reusable machinery. Every item in the plan’s “done when” list:

RequirementWhere it lives
Groq callable through a provider abstractionpackages/ai/src/provider/
Future providers swappableprovider/index.ts registry + AI_BASE_URL
Responses validatedpackages/ai/src/schemas/ (zod, 8 contracts)
Errors handledAiError taxonomy + bounded retry with backoff
Knowledge stored & retrievedKnowledgeItem table + knowledge/index.ts
Context builders existcontext/index.ts — page, site, knowledge
AI has independent queuesai-page, ai-site, ai-competitor
Results cachedcache/index.ts — SHA-256 over everything that shapes the answer
Prompt/knowledge versions traceableAiResult.promptVersion, .knowledgeVersion

Design decisions worth knowing

  • No SDK. The provider talks to Groq’s OpenAI-compatible endpoint over fetch. The surface used is three fields of one JSON body; a dependency-free provider is one less thing on a release treadmill. The same class serves any OpenAI-compatible endpoint.
  • Validation is ours, not theirs. The request asks for json_object rather than a provider-side JSON schema, because schema support varies by model — and we validate with zod afterwards regardless. The contract is enforced on our side.
  • A failure is a row, not a gap. Provider outages and invalid output both write an AiResult with status: failed or invalid. Without that, “why is there no suggestion on this page” has no answer anyone can look up.
  • Retries are bounded inside the AI layer, so BullMQ does not retry on top of them. A 401 fails on the first attempt rather than making three identical doomed requests.
  • Missing API key disables AI; it does not crash the worker. The crawler and deterministic scoring must keep working with no provider configured.

8. Worked example, end to end

A dental clinic runs a Deep analysis on brightsmile.example/services/whitening. Here is what actually happens.

Step 1 — the crawler produces facts

url:        https://brightsmile.example/services/whitening
statusCode: 200
title:      "Whitening"
metaDesc:   null
h1:         "Teeth Whitening"
h1Count:    1
wordCount:  184
schemaCount: 0
pageType:   "service"  (confidence 0.85)

The deterministic layer writes three PageIssue rows: meta (fail), words (warning, under the 300 threshold), schema (warning).

Step 2 — the job enqueues

Crawl completes → ai-page queue receives { pageId, mode: "deep" }. It does not share the crawl queue, so a slow provider can never stall a crawl.

Step 3 — context is assembled

buildPageContext() gathers the evidence and names what is missing:

evidenceGaps: [
  "No structured data was found on the page."
]

That list goes into the prompt verbatim. It is what turns “the model invented an answer” into “the model reported it lacked the evidence”.

Step 4 — knowledge is retrieved

The failing checks are ["meta", "words", "schema"]. Retrieval joins on checks and returns, among others:

  • seo-onpage-meta-description-criteria — short, unique to one page, carries the key points
  • seo-qrg-mc-quality-dimensions — effort, originality, skill, accuracy
  • seo-qrg-page-type-not-quality — page type does not determine quality
  • seo-sd-eligibility-not-guarantee — markup creates eligibility, not a rich result

Two policies attach automatically via appliesToChecks: policy-word-count and policy-title-meta-length. Myth items are returned separately, in contradictions — never mixed into advice.

Step 5 — the cache is checked

sha256( feature + mode + model + promptVersion + knowledgeVersion
        + evidence + businessContext )

Change the page, the business context, the corpus, or the prompt, and the key changes. A stale answer cannot survive a re-crawl or a knowledge re-ingest.

Step 6 — generation, and the difference the policies make

Without the knowledge layer — what a bare LLM returns:

“This page is under 300 words. Google prefers longer content — expand it to at least 800 words. Your title is too short; aim for 50-60 characters. Add schema markup to get rich results.”

Four claims, three of them false. Google publishes no word-count preference, no title length, and markup never guarantees a rich result.

With the knowledge layer — what the validated output contains:

Meta description (high severity, actionable) — The page has no meta description. Google generates snippets mainly from page content but may use a description when it describes the page better for a query. Write one that is unique to this page and names the treatment, the clinic and the location.

Content depth (medium, actionable) — The page introduces whitening but does not cover what a first-time patient needs before booking: what the appointment involves, how long results last, aftercare, and what it costs. Adding those is the gap — not a word count.

Structured data (medium, actionable) — No markup found. A Service or Dentist type matching the visible content would make the page eligible for richer presentation. Eligibility is not a guarantee; display remains Google’s decision.

groundedIn: ["evidence.metaDescription", "evidence.wordCount", "seo-onpage-meta-description-criteria", "seo-qrg-mc-quality-dimensions", "seo-sd-eligibility-not-guarantee"]

Note what the policies changed. “Under 300 words” became what the page is actually missing. “Add schema to get rich results” became “eligible for”. No character target appears anywhere, because none is documented.

Step 7 — validation, then storage

The response is parsed against pageRecommendationSchema. An empty groundedIn is a validation failure — a recommendation that cites nothing never reaches the database. On success an AiResult row records the provider, model, prompt version, knowledge version, input hash and token counts.

crawl → deterministic checks → PageIssue rows
    ↓
ai-page queue → buildPageContext() + evidenceGaps
    ↓
retrieveKnowledge(checks) → items + contradictions + policies
    ↓
cache lookup (miss) → generateStructured() → retry/backoff
    ↓
zod validation → reject or AiResult row

9. How to run it

# 1. start infrastructure
pnpm db:up

# 2. apply the Phase 1 migration (creates the two knowledge tables)
pnpm db:deploy

# 3. load the corpus into Postgres — 170 items, 7 policies
pnpm knowledge:ingest

# 4. add a Groq key to .env
AI_PROVIDER=groq
AI_MODEL=llama-3.3-70b-versatile
AI_API_KEY=gsk_...

# 5. run
pnpm dev

Steps 2 and 3 were not run on this machine — Docker Desktop was not running. The migration SQL was written by hand and verified column-for-column against Prisma’s own generated DDL (43 columns and 3 indexes on KnowledgeItem, 14 on KnowledgePolicy, exact match). It will apply cleanly.

Leaving AI_API_KEY empty is supported: AI features report unavailable, and the crawler and scoring work exactly as before.

10. What Phase 2 adds

The foundation is deliberately broader than what is wired. All eight output contracts, the three queues and the full context layer exist; Phase 1 ships one real feature — page recommendations — so the pipeline is proven rather than theoretical.

Phase 2 adds the remaining page features (title, meta, content, schema, internal links) on top of the same runAiFeature() call. Each is a schema and a prompt; none requires changes to the provider, retrieval, caching or queue layers.

One field is reserved for it: KnowledgeItem.pageTypes is empty today and gets populated in Phase 2, when page-type-specific knowledge is added.

Known gaps — unresolved, not missing

Ranking weights, per-engine AI citation formulas, ChatGPT’s retrieval backend, whether any production system reads llms.txt, local SEO ranking specifics, and the durability of the GEO effect sizes.

45 items cite sources not archived in raw/ and were not re-read. Adding those PDFs is the highest-value next step; the source register ranks them by how many items depend on each.
